    Changelog¶

    All notable changes to Spring AI ACP Harness Client are documented here. The project follows Semantic Versioning (MAJOR.MINOR.PATCH).

    [0.6.0] - Unreleased¶

    Changed¶

    • Breaking: Java packages move from org.springaicommunity.acp.* to org.springaicommunity.acp.harness.*, to match the artifacts and the properties. Update your imports, and any logging.level.org.springaicommunity.acp setting, which otherwise stops matching without an error. The JDBC schema for MCP OAuth moves with them, to org/springaicommunity/acp/harness/mcp/oauth/acp-mcp-oauth-schema.sql.
    • Breaking: AcpAgentClient becomes AcpHarnessClient, along with DefaultAcpHarnessClient, AcpHarnessClientPool, AcpHarnessClientFactory and AcpHarnessClientException, and the bean acpAgentClient becomes acpHarnessClient. ACP's two roles are client and agent, so a client type named for both was ambiguous, and it matched neither the project's artifacts nor its properties. Replace AcpAgentClient with AcpHarnessClient to migrate. Types that describe the agent keep their AcpAgent names, as do AcpHarnessClient.AcpAgentResponse and AcpAgentStream.
    • Breaking: configuration properties move from spring.acp.* to spring.ai.acp.harness.*, and environment variables from SPRING_ACP_* to SPRING_AI_ACP_HARNESS_*. The old root is shared with acp-autoconfig (spring.acp.client.*, spring.acp.agent.*), and the new one follows the spring.ai.* convention of the Spring AI Community projects. Update your configuration: the old keys are no longer read, and nothing reports them, so a spring.acp.*.enabled=false stops taking effect. The acp: config import prefix, metric names and Java packages are unchanged.
    • Snapshots are published to the Maven Central snapshot repository, and releases will go to Maven Central. Versions up to 0.5.0 remain in the Artifact Registry repository.
    • The reference documentation moved from a single docs/user-guide.html to a versioned MkDocs site, published to GitHub Pages from docs/.

    Fixed¶

    • A new session that failed while being configured, such as an unsupported model with on-unsupported: fail, stayed open on the agent until session-ttl, with its MCP route still live. In a pool these sessions used up capacity, so later turns were refused with a "holding its maximum" error instead of reporting the real failure. A session that was already open is kept, so a bad per-turn override does not end a conversation. The same applied to a session attached with sessions().load or resume, which stayed loaded on the agent; it is now closed there too.
    • A session/new the agent answered after the caller stopped waiting, as when a cancelled turn interrupts its thread, named a session nothing could close; it is now closed when the answer arrives. A session/new not answered within timeout now fails with an AcpHarnessClientException instead of an IllegalStateException; an answer after that is dropped by the ACP SDK, so a session created that late still stays on the agent.
    • Subscribing twice to one throwaway AcpAgentStream now runs two sessions. They used to share one, so the first to finish could close it under the other.
    • A closed AcpHarnessClientPool would start new agents on request, and a connection still being built when the pool closed was never closed. A closed pool now refuses work with an AcpHarnessClientException, and a connection that finishes building after the close is closed at once. Closing does not interrupt or wait for a connect in progress.

    [0.5.0] - 2026-10-20¶

    Changed¶

    • Renamed from Spring AI ACP to Spring AI ACP Harness Client, ahead of moving to the Spring AI Community organisation. Every artifact moves from spring-ai-acp-* to spring-ai-acp-harness-client-* (for example spring-ai-acp-boot-starter-goose becomes spring-ai-acp-harness-client-boot-starter-goose) under the same org.springaicommunity groupId; update your dependencies. Java packages (org.springaicommunity.acp.*) and configuration properties (spring.acp.*) are unchanged.
    • The live-test switches follow the new name: -Dspring-ai-acp-harness-client.test.live=true, -Dspring-ai-acp-harness-client.test.<runtimeId>.model and -Dspring-ai-acp-harness-client.test.registry.live=true.
    • The agent now sees the client as spring-ai-acp-harness-client in ACP initialize, as does an MCP authorization server registering it when spring.application.name is unset. State kept on disk keeps the former name so an upgrade finds it: the registry cache (~/.spring-ai-acp/agents), the .spring-ai-acp-skill marker, and the MCP sign-in file of an application without a spring.application.name. Such an application's console does take the new name, for its title and for its input history, which therefore starts afresh.
    • Every type named for the agent now says AcpAgent, so that it no longer reads as one of Spring AI's own agent types beside it: AgentClient becomes AcpAgentClient (and its nested AgentResponse and AgentStream, AcpAgentResponse and AcpAgentStream), AgentSession/AgentSessions become AcpAgentSession/AcpAgentSessions, AgentEvent becomes AcpAgentEvent, and likewise AcpAgentOptions, AcpAgentSettings, AcpAgentInfo, AcpAgentNotice, AcpAgentExecutor, AcpAgentClientException, UnsupportedAcpAgentOperationException and UnsupportedAcpAgentOptionException. The adapter SPI follows (AcpAgentRuntime, AcpAgentRuntimeProvider, AcpAgentLaunchSpec, AcpAgentEnvironment), as does the test kit (AcpAgentRuntimeContract, AcpAgentProbe, ScriptedAcpAgent, LiveAcpAgents) and every internal type. The rule is mechanical, so replacing each \bAgent…\b type name with its AcpAgent… spelling migrates an application; packages, bean names, configuration properties and the standalone configuration file are unchanged. Two exceptions: the transport for a supervised served agent, WebSocketAgentTransport, becomes SupervisedWebSocketTransport, since the SDK's *AcpAgentTransport names are for the agent's side of the connection; and AcpAgentSession shares its simple name with the SDK's agent-side com.agentclientprotocol.sdk.agent.AcpAgentSession, a class an application using this library has no reason to import.
    • A standalone configuration file must now be imported with the acp: prefix: spring.config.import: optional:acp:agents.yaml. A bare optional:agents.yaml is no longer claimed by name, because Boot asks this library's resolver before its own, and claiming the name took the file from any other library that reads an agents.yaml. Without the prefix Boot now loads the file as ordinary configuration, so its keys miss spring.acp and are silently ignored: add acp: to the import.

    Fixed¶

    • spring-ai-acp-harness-client-mcp-oauth: a sign-in that had lapsed — its refresh token no longer honoured — was never cleared, so the user was never asked to sign in again and every session after failed to load the server (with goose, "discover and legacy initialize both failed"). The authorization server behind the Tanzu MCP gateway refuses such a refresh with a 401, which Spring Security reads as invalid_token_response instead of invalid_grant; an OAuth error in a 401 from the token endpoint is now read as what it says.
    • spring-ai-acp-harness-client-mcp-oauth: an expired token is now refreshed as the session opens, so a refresh the server refuses leads straight to signing in again (a browser in mode: local, a redirect in mode: web) instead of failing the session's first request. A refresh that fails without a refusal, such as an authorization server that is down, still keeps the token for next time.

    [0.4.0] - 2026-10-04¶

    Changed¶

    • ACP Java SDK 0.18.0, with its Jackson 3 JSON module (acp-json-jackson3). The SDK no longer carries a JSON implementation in acp-core, and this library now uses Jackson 3 throughout, as Spring Boot 4 and Spring AI 2 do. Jackson 2 no longer arrives through Spring AI ACP: an application that used com.fasterxml.jackson.databind without declaring it must now add it itself. Jackson's annotations (com.fasterxml.jackson.annotation) are unchanged.
    • Spring Boot 4.1.1, which brings Jackson 3.1.5, the version the SDK is built against.

    Fixed¶

    • With goose serve, an answer to the agent (a permission decision, a file read, a terminal result) could be dropped when it was sent at the same moment as a new request, leaving that turn waiting until it timed out. The SDK fixed the same race in its own WebSocket transport in 0.18.0.
    • With goose serve, a request in flight when the connection drops now fails at once instead of waiting out the request timeout, so the turn ends with an error straight away.

    [0.3.1] - 2026-10-01¶

    Added¶

    • auth: provided for an MCP server whose credentials come from the application's own McpCredentialsProvider. Such a server may omit url: the provider supplies the upstream with McpCredentials.routed(url, credentials) when the session opens, as a credential broker that issues a token together with its endpoint does. A URL-less server the provider does not route is left out of that session instead of refusing it.
    • A Tanzu AI Models (GenAI) service bound on Cloud Foundry becomes the provider with no configuration. Its OpenAI-compatible endpoint is used as spring.acp.provider.base-url and api-key, and when no spring.acp.model is set, the first TOOLS-capable model in its catalog is chosen.
    • An explicitly configured provider wins.
    • spring.acp.tanzu-ai.enabled and service-name control it.
    • CODEX_ACP_CLI_PATH names a local codex-acp for the Codex runtime to launch in place of npx, as GOOSE_CLI_PATH and OPENCODE_CLI_PATH do for theirs. The Codex supply buildpack exports it. spring.acp.runtimes.codex.command still wins, and so does an explicit package, which asks for npx.
    • Goose's todo list arrives as AgentEvent.PlanUpdated. Goose keeps its task list in a tool and sends no ACP plan update, so each todo__todo_write call is read as the agent's plan instead of being reported as a tool call. AgentRuntime.planOf is the hook any adapter can use for an agent that does the same.
    • Helpers for runtime adapters, so their shared rules live in core:
    • AgentEnvironment.layered builds a launch environment in the order every adapter uses. Agent defaults come first, then provider credentials, then the tier-3 env block, which wins.
    • Executables.fromEnvironment reads an executable path from an environment variable such as GOOSE_CLI_PATH, and checks it at startup.
    • AgentSettings.findModel() returns the requested model, or empty when it is blank.

    Changed¶

    • AcpProperties and its nested types are records, bound through their constructors. Code that reads them uses record accessors (properties.model(), properties.pool().sessionTtl()) in place of getters. Property names, defaults and metadata are unchanged, except that spring.acp.protocol.max-version now lists its default (1) in the metadata. A test that declared new AcpProperties() as a bean registers it with @EnableConfigurationProperties(AcpProperties.class) instead.

    Fixed¶

    • OpenCode sessions no longer call MCP servers as another user, or through a closed session's route. OpenCode keeps one MCP client per server name for its whole process, replaced by each session/new, so every session used the route of the one opened last. A runtime now declares this with AgentRuntime.mcpScope() (PROCESS for OpenCode). The pool then keeps each such process to one principal at a time, restarting an idle process before it serves someone else, and McpAccess gives the principal one route shared by all of their sessions, held until the last closes. spring.acp.pool.max-processes caps how many users hold OpenCode sessions at once, and each costs a whole OpenCode process (about 650 MB); see "Processes, users and memory" in the user guide.

    [0.3.0] - 2026-09-24¶

    Initial release as Spring AI ACP, under the org.springaicommunity groupId and the Apache License 2.0.

    Agents and runtimes¶

    • AgentClient, a fluent client that drives any Agent Client Protocol v1 coding agent and streams each turn as AgentEvents, with exactly one terminal event per turn.
    • Compiled runtime adapters for Goose, Codex (codex-acp) and OpenCode, selected by spring.acp.runtime, and spring-ai-acp-boot-starter-registry, which launches any agent the ACP registry publishes from a cached catalogue, with SHA-256-verified downloads.
    • A supervised goose serve over WebSocket, as an alternative to stdio.
    • ACP version negotiation; v2 is behind a feature flag and refused.

    Configuration¶

    • Three configuration tiers: portable (spring.acp.*), negotiated (model, mode and provider, resolved against the options the agent advertises, with on-unsupported = fail/warn/ignore), and runtime-specific (spring.acp.runtimes.<id>.*).
    • Bring-your-own OpenAI-compatible endpoints through spring.acp.provider.base-url, with the endpoint's own model listing deciding which models are valid.
    • A standalone agents.yaml, loaded as Spring config data.

    Sessions, MCP and skills¶

    • Capability-gated session list, load, resume and delete, with connection pooling and idle session sweeping.
    • MCP servers declared per session, with credentials kept out of the agent: HTTP servers that need them are reached through a loopback proxy, one unguessable route per session.
    • spring-ai-acp-mcp-oauth: per-user MCP-spec OAuth, redirecting through Spring Security in a web application or signing in through a loopback browser flow in a terminal one.
    • Detection of MCP servers that goose fails to load, which ACP never reports on the wire, surfaced as AgentClient.notices() and acted on through spring.acp.mcp.on-server-failure.
    • Skills installed from Git (optionally pinned to a commit) into the workspace.

    Permissions and the workspace¶

    • Permission policies (deny, allowlist, auto-approve and ask), with ask answered by a person through a PermissionPrompt.
    • A workspace jail that confines the agent's filesystem and terminal requests by real path.

    Integrations¶

    • AcpChatModel, which publishes the agent as a Spring AI ChatModel.
    • An opt-in HTTP endpoint, and the AgentExecutor facade.
    • spring-ai-acp-console, a terminal chat over the application's agent for prototyping it.
    • A Micrometer observation per turn and per tool call, and AgentEvent.UsageUpdated.

    Testing¶

    • spring-ai-acp-test: AgentRuntimeContract, the cross-adapter contract test; AgentProbe, which gates live suites on a real session; and ScriptedAgent, a fake agent speaking raw JSON-RPC for wire-format tests. Live-agent suites are opt-in with -Dspring-ai-acp.test.live=true.
